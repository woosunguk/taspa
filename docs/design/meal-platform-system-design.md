# TASPA 식대 플랫폼 — 시스템 진화 설계

> 출발점(식당정보 + QR 식권결제 + 조직 후불정산)을 기반으로, TASPA가 어떤 시스템으로 진화해야 하는지의 목표 아키텍처와 단계별 경로.
> 배경 리서치: [meal-platform-design.md](../research/meal-platform-design.md). 시각 요약: 아티팩트 참조.

## 0. 설계 명제

- **TASPA는 신원(IdP)으로 남는다.** 식대 결제·정산은 TASPA를 신뢰 기반으로 삼는 **별도 백엔드**로 올린다. (ADR 0001 경계 유지)
- **후불형 폐쇄루프.** 개인 선불충전 없음 → 선불전자지급수단 규제 회피. 현금환급 불가 → 식대 비과세(월 20만) 요건 충족.
- **QR = 초단명 서명 토큰.** TASPA의 JWK 서명·회전 스택을 재사용해 30~60초 1회용 결제 토큰을 발급. 금액·개인정보는 QR에 넣지 않는다.
- **돈의 진실은 별도 불변 원장에.** `audit_events`(보안 감사)와 분리한 append-only 이중부기 원장.

## 1. 색으로 읽는 경계

이 문서는 두 색으로 컴포넌트의 소속을 표시한다.
- **틸(TASPA)** — 신원·서명키·조직소속·인가. 이미 존재하는 자산.
- **퍼시먼(식대)** — 식당·한도·거래·원장·청구·정산. 신규 개발.

## 2. 시스템 진화 4단계

| 단계 | 범위 | 해금되는 능력 | 규제/자금 |
|------|------|--------------|-----------|
| **L0 기본** | 식당정보 · QR 식권결제 · 조직 후불정산 | 사용자가 전달한 최소 구조 | — |
| **L1 MVP** | 폐쇄루프 · 온라인 CPM · 한도엔진 · 이중부기 원장 · 월청구 · 세금계산서 위탁발행 | 1개 조직 파일럿, 실제 결제·정산 폐순환 | 외부 PG/에스크로 위탁(등록 예외) |
| **L2 플랫폼** | 다중소속(파견/겸직) · 부서예산 · MPM 보조채널 · 무단말 온보딩 · 부분취소/환불 · 이상탐지 | 다조직·다식당 확장, 여신관리 | 여전법 경로·rolling reserve |
| **L3 에코시스템** | PG 등록(자체정산) · 오프라인 floor-limit · 오픈뱅킹 자동이체 · 카드 공통QR 브리징 · 다지역/다통화 | 규모 스케일·정식 규제화 | PG 등록 or 여전법 확정 |

핵심: **L0→L1은 "폐순환을 닫는 것"**(결제→원장→청구→정산→대사), L1→L2는 **"조직·식당 다변화 + 신용관리"**, L2→L3은 **"자체 결제 인프라화"**.

## 3. 아키텍처 지도 (바운디드 컨텍스트)

```
── TASPA 측 (신원, 재사용) ─────────────┐   ┌─── 식대 측 (신규, 별도 백엔드) ────────────
  · 신원 (users, sub=UUID)              │   │  · 식당 디렉터리 (merchant)
  · 서명키 스택 (JWK 회전/JWKS)         │   │  · 소속/조직 (organizations, memberships)*
  · OIDC / M2M (client_credentials)     │   │  · 한도/정책 (entitlement)
  · 조직경계 원천 (sso_domains)         │   │  · 거래 (transaction)
  · 관리·감사·인가                       │   │  · 원장 (ledger, 불변 이중부기)
                                         │   │  · 청구 (billing, 조직 월청구)
  * organizations/memberships 는 신원과  │   │  · 정산 (settlement, 식당 payout)
    가까워 TASPA 내 테넌시로 신설         │   │
─────────────────────────────────────────┘   └────────────────────────────────────────────
                     └── client_credentials(M2M) 토큰으로 서비스간 인증 ──┘
```

- 경계 규칙: 식대 서비스는 **자체 신원 저장소를 두지 않고** TASPA 토큰 클레임(`sub`/`org_id`/`merchant_id`)만 참조.
- MVP는 식대 측을 **모듈러 모놀리스**(패키지·스키마 논리 분리)로 시작 → 트래픽 성장 시 물리 분리.

## 4. 핵심 흐름 ① QR 결제

1. 직원앱 → TASPA: 결제토큰 요청(로그인 세션 + 활성 org 컨텍스트)
2. TASPA → 직원앱: **초단명 서명 토큰**(JWK 서명, 30~60초, jti·exp) → QR 표시
3. 식당 POS → 거래서비스: QR 스캔 + **금액 입력**(금액은 POS가 결정, QR엔 없음)
4. 거래서비스: JWKS로 서명·만료·jti 1회성 검증
5. 거래서비스 → 한도서비스: 식사시간창·일한도·화이트리스트 정책 확인
6. 한도 통과 시 거래서비스 → 원장: 이중부기 기록(조직 미수 + 식당 미지급 동시 발생)
7. 거래서비스 → POS: 승인·영수 / 직원앱: 결제완료 통지

**다층 방어**: 단명 exp(재사용 창 최소) · jti 1회성(재생 방지) · 서버측 한도 실시간 조회(토큰 상태없음 보완) · 금액을 POS가 결정(QR 금액 위조 무의미) · 기기분실 시 step-up/원격 로그아웃(TASPA 자산).

## 5. 핵심 흐름 ② 후불 정산 + 원장

```
결제(거래)
   │  이중부기: (차) 조직 미수  / (대) 식당 미지급        ← 결제 순간 동시 발생
   ▼
append-only 원장 ──┬─▶ [월말] 조직별 집계 ─▶ 세금계산서 위탁발행 1건 ─▶ 조직 청구·수납
                   └─▶ 식당별 집계 ─▶ 외부 PG/에스크로 ─▶ 식당 payout(수수료 차감)
3-way 대사: 거래 합계 ↔ 조직 청구 합계 ↔ 식당 정산 합계  (일치 검증·분쟁 정합)
```

- **이중부기 예시** (12,000원 점심 1건):

  | 계정 | 차변 | 대변 |
  |------|-----:|-----:|
  | 조직 미수(A사) | 12,000 | |
  | 식당 미지급(B식당) | | 12,000 |

- 후불 누적(accrual) → 월말 확정 → 조직엔 **1건 세금계산서**(개별 식당 계산서 수취 대체 = 핵심 효익), 식당엔 정산.
- 후불형 고유의 **신용위험**(조직 미수·연체)은 aging·여신한도로 L2에서 관리.

## 6. 한도 / 정책 엔진 (Entitlement)

- 정책 계층: 플랫폼 기본 → 조직 정책 → (부서 정책) → 개인 예외. 결제 컨텍스트로 라우팅.
- 규칙 차원: **식사시간창**(예 점심 11:00~14:00) · **일/월 한도**(1일 1식, 12,000원) · **사용처 카테고리**(음식점 O, 편의점·커피 X — 비과세 요건과 직결) · 주말/휴일 규칙.
- 리셋 시맨틱: 일/월 경계, 조직 회계기준일. 집행은 결제 승인 경로에서 **동기 확인**(초과 시 단순 거절, L1).

## 7. TASPA 자산 재사용 맵

| 재사용 (그대로/소폭) | 신규 개발 (식대 측) |
|----------------------|---------------------|
| 신원 `sub`(UUID) = 결제 주체 안정키 | 식당 디렉터리 서비스 |
| **JWK 서명스택** = QR 결제토큰 서명/검증 (EC 키 프로파일만 추가) | 한도(Entitlement) 서비스 |
| OIDC `client_credentials` = 서비스간 인증 | 거래 서비스 |
| `sso_domains`/`federated_identities` = "직원↔회사 소속" 판정 | **이중부기 원장 서비스** |
| Resource Server 스타터 = issuer-uri만으로 JWT 검증 | 청구 · 정산 서비스 |
| 관리콘솔·감사·step-up·원격로그아웃 | POS 앱 · 직원앱 · 조직/식당 콘솔 · 외부 PG 연동 |

**TASPA 1순위 수정 지점** (코드 근거): `AdminClientService.ALLOWED_SCOPES`가 `openid/profile/email` 하드코딩(L212) → `meal.pay`·`merchant.*`·`settlement.*` 등 화이트리스트 확장. `TokenCustomizer`에 `org_id`/`org_role`/`merchant_id` 클레임(클라이언트 허용 역할 ∩ 사용자 보유 역할, 최소권한). `organizations`/`org_memberships` 신설(ADR 0002 대안 C). QR 결제토큰 발급 엔드포인트 + EC 키 프로파일.

## 8. 결정적 리스크 & 설계 원칙 (비타협)

1. **⚠️ PG 규제** — TASPA가 결제대금을 받아 식당에 재정산하면 전자금융거래법 PG 등록 트리거(미등록 시 형사처벌). → **MVP는 외부 PG/에스크로에 자금정산 위탁**(등록 예외), 규모 확대 시 PG 등록 로드맵. **법률자문 필수.**
2. **선불 모델 금지** — 개인 선불충전을 도입하면 선불전자지급수단 규제(충전금 100% 별도관리). 후불 유지.
3. **원장 분리** — 금전 원장을 `audit_events`에 섞지 않는다. 마감·정합성·bi-temporal 필요.
4. **경계 유지** — 식대 도메인을 TASPA에 흡수하지 않는다. TASPA는 IdP.
5. **QR에 가치·PII 없음** — 금융위 QR 표준 준수, 금액은 POS가 결정.
6. **세무 태깅** — 비과세 20만 초과분·비인정 사용처를 원장 메타데이터로 과세 분리.

## 9. 로드맵

- **Phase 0 (2~3주)** — TASPA 최소 확장(organizations/memberships, scope 화이트리스트, org/role 클레임, EC 결제키, QR 발급 엔드포인트) + **법률/세무 자문 착수**.
- **Phase 1 MVP** — 폐쇄루프 CPM 결제 · 한도엔진 · 이중부기 원장 · 월청구·세금계산서 위탁발행 · 외부PG 위탁 정산 · 3-way 대사 · 1조직 파일럿.
- **Phase 2 플랫폼** — 다중소속 · 부서예산 · MPM 보조 · 무단말 온보딩 · 부분취소/환불 · 이상탐지 · 여신관리.
- **Phase 3 에코시스템** — PG 등록(자체정산) · 오프라인 floor-limit · 오픈뱅킹 · 카드 공통QR 브리징 · 다지역/다통화.
