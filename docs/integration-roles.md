# 조직 역할을 연동 서비스로 전파하기 (`org.roles`)

taspa 에서 조직관리자가 만든 **커스텀 역할**(예: "회계 담당")을, 연동 서비스가 자기 인가에 그대로 쓸 수
있게 토큰에 실어 보낸다. 그 전까지 연동 서비스는 사용자가 어느 조직 소속인지(`org_id`)까지만 알 수
있었고, "이 사람이 우리 서비스에서 무엇을 할 수 있는가"는 서비스마다 별도 권한 테이블을 두고 **또 한 번
관리**해야 했다.

## 한눈에

```
조직관리자가 역할 정의  →  구성원에게 부여  →  로그인 → 토큰에 roles 클레임 → 연동 서비스가 인가
      (조직 콘솔 "역할" 탭)                        (선언한 이름 ∩ 보유한 이름)
```

## 1. 클라이언트 쪽 준비 (플랫폼 관리자)

`/admin/clients` 에서 두 가지를 설정한다.

| 항목 | 값 | 없으면 |
|---|---|---|
| scope | `org.roles` 추가 (보통 `org.read` 와 함께) | 클레임 미발급 |
| 선언 역할 이름 | 이 서비스가 **인가에 쓸** 역할 이름 목록 | 클레임 미발급 |

★**둘 다 필요하다(fail-closed).** scope 만 있고 선언이 비면 `roles` 는 실리지 않는다.

### 왜 "선언"이 필요한가

선언 없이 사용자의 역할을 전부 실어 보내면 두 가지가 무너진다.

1. **조직 구조가 누출된다.** 역할 이름은 조직 내부 정보다("보안감사", "임원비서"). 연동 서비스마다
   그 목록이 흘러갈 이유가 없다.
2. **조직이 역할을 하나 추가할 때마다 모든 연동 서비스의 인가 입력이 조용히 바뀐다.** 선언이 있으면
   서비스가 아는 이름만 들어오므로, 조직의 자율 편집이 서비스 동작을 예고 없이 바꾸지 못한다.

실제로 실리는 값은 **선언한 이름 ∩ 사용자가 실제로 가진 이름**이다. 선언만 하고 사용자가 안 가졌으면
당연히 안 실리고, 가졌는데 선언 안 했으면 실리지 않는다.

## 2. 토큰 모양

기존 org 클레임과 **대칭**이라 해석 규칙을 새로 익힐 필요가 없다.

```jsonc
{
  "sub": "…UUID…",
  "org_id": "11111111-…",          // 대표 조직
  "org_role": "MEMBER",            // 멤버십 역할(MEMBER|ORG_ADMIN)
  "roles": ["회계 담당"],           // ★ 대표 조직의 커스텀 역할 (org_id 와 짝)
  "orgs":      [{ "id": "…", "role": "…" }],        // 여러 조직일 때만
  "org_roles": [{ "org": "…", "roles": ["…"] }]     // 여러 조직일 때만
}
```

★**`roles` 는 항상 `org_id` 와 같은 조직의 것이다.** 대표 조직에 해당 역할이 없으면 `roles` 는 아예
싣지 않고 `org_roles` 로만 알린다 — 짝이 안 맞는 값을 그 자리에 넣으면, 조직을 확인하고 역할로 인가하는
서비스가 **다른 조직의 권한을 주게 된다**.

`org_role`(멤버십 역할)과 `roles`(커스텀 역할)는 **다른 축**이다. 전자는 taspa 조직 관리 권한,
후자는 조직이 정의한 이름표다.

## 3. 서비스 쪽 사용 (Spring Boot)

`taspa-client-spring-boot-starter` 를 쓰면 변환기가 자동 등록된다.

```yaml
taspa:
  client:
    issuer-uri: https://auth.example.com
    # 이 서비스가 담당하는 조직. 지정하면 그 조직의 역할만 읽는다.
    # 미지정이면 토큰의 대표 org 역할을 쓴다. 어느 쪽이든 여러 조직의 역할을 합치지 않는다.
    org-id: 11111111-2222-3333-4444-555555555555
    # role-authority-prefix: "ROLE_"   # 기본값
    # roles-enabled: false             # 끄면 scope 권한만
```

```kotlin
@PreAuthorize("hasRole('회계 담당')")
@GetMapping("/invoices")
fun invoices(): List<Invoice> = …
```

`SCOPE_*` 권한은 그대로 유지된다 — 변환기는 역할 권한을 **추가**만 한다.
자체 `JwtAuthenticationConverter` 빈을 등록하면 스타터는 물러난다(남의 인가 규칙을 덮지 않는다).

### 다른 스택

클레임을 직접 읽으면 된다. 위의 "`roles` 는 `org_id` 와 짝" 규칙만 지키면 된다:

```ts
const orgId = claims.org_id;
const roles = orgId === MY_ORG ? (claims.roles ?? []) : rolesOf(claims.org_roles, MY_ORG);
```

## 4. 운영자가 알아야 할 것

### 회수는 즉시가 아니다 (JWT 의 성질)

역할을 해제하면 **taspa 안에서는 즉시** 권한이 사라진다(인가는 항상 DB 의 정책을 읽는다).
그러나 **이미 발급된 액세스 토큰의 `roles` 클레임은 만료까지 남는다** — 기본 TTL 15분.

- 급히 차단해야 하면: 조직 콘솔에서 그 사람의 **세션을 종료**하고, 필요하면 멤버십을 정지한다.
  (리프레시가 막히므로 최대 노출 창이 액세스 토큰 잔여 시간으로 제한된다.)
- 연동 서비스가 즉시 반영을 요구한다면 `roles` 를 캐시로 쓰지 말고 매 요청 introspection 을 하거나,
  taspa API 로 확인해야 한다. **이 문서의 방식은 "빠르지만 15분까지 늦을 수 있다"는 계약이다.**

### 역할 이름을 바꾸면 연동 서비스가 그 역할을 잃는다

이름이 곧 키다. 조직이 "회계 담당"을 "재무 담당"으로 바꾸면 선언 목록(`회계 담당`)과 교집합이 없어져
클레임에서 빠진다 — **닫히는 방향이라 안전하지만**, 그 서비스의 담당자는 권한이 사라진 이유를 모른다.
이름 변경 전에 연동 서비스의 선언 목록을 함께 갱신할 것.

### taspa 자신은 이 클레임을 인가에 쓰지 않는다

`roles` 는 **연동 서비스용 힌트**다. taspa 의 인가는 IAM 정책 엔진이 DB 를 읽어 판정한다
(`docs/architecture.md`, CLAUDE.md "AWS IAM 스타일 정책 RBAC"). 그래서 토큰을 위조하지 않는 한
이 클레임으로 taspa 권한이 넓어지는 경로는 없고, 위조는 서명 검증이 막는다.

## 5. 확인 방법

1. `/admin/clients` 에서 클라이언트에 `org.roles` scope + 역할 이름 선언
2. 조직 콘솔 "역할" 탭에서 역할을 만들고 테스트 계정에 부여
3. 그 계정으로 연동 서비스에 로그인 → 액세스 토큰을 디코드해 `roles` 확인
4. 역할을 해제하고 **다시 로그인** → `roles` 에서 사라지는지 확인
   (해제 직후 기존 토큰에 남아 있는 것은 위의 "회수는 즉시가 아니다"대로 정상)
